iÉtat des lieux — à lire en premier

Ce guide liste des actions manuelles, à effectuer depuis des interfaces web (Hub, Vercel, Supabase) auxquelles le code n'a pas accès. Elles complètent — et ne remplacent pas — les correctifs déjà appliqués dans le code (voir AUDIT_SECURITE.md pour le détail technique : contrôle d'accès sur les routes de gestion d'appareils, XSS corrigé, rate limiting applicatif, en-têtes de sécurité HTTP, validations d'entrée).

Important Aucune preuve d'intrusion réelle n'a été constatée pendant cet audit — ce document ne part pas du principe qu'une fuite a eu lieu. S'il y a un doute concret (comportement anormal observé, alerte du Hub, etc.), traitez ce doute avec la section "En cas de doute d'intrusion" en priorité.

1Rotation des clés API Recommandé

Même si aucune fuite n'est confirmée, une rotation périodique des secrets est une bonne hygiène — et devient indispensable si l'un d'eux a pu être exposé (capture d'écran partagée, commit accidentel, etc.).

  1. Clé Hub (mbs_...) — Super Admin Hub → API Keys → révoquer l'ancienne, en créer une nouvelle avec les mêmes scopes (auth:*, licenses:verify) → mettre à jour MBEUK_HUB_API_KEY dans Vercel → redéployer.
  2. Clé Brevo (si SAAS_BREVO_API_KEY est utilisée) — console Brevo → SMTP & API → révoquer/régénérer.
  3. Clé Chariow / paiement — si votre compte Chariow ou Stripe a une clé exposée, la régénérer depuis leur tableau de bord respectif.
  4. Ne collez jamais une clé réelle dans un chat IA, un ticket de support, un message Slack/WhatsApp, ou un fichier commité sur GitHub — même temporairement.

2Row Level Security — Supabase BYODB Important

Chaque église connecte son propre projet Supabase gratuit via le module "Cloud Sync BYODB" (indépendant du Hub). Ce projet Supabase est configuré par l'utilisateur final, pas par vous — mais un rappel dans votre documentation utilisateur est recommandé :

  • Activer RLS (Row Level Security) sur toutes les tables créées pour la synchronisation, même en usage mono-église — évite qu'une clé anon exposée ne donne un accès total à la base.
  • Ne jamais utiliser la clé service_role côté client (uniquement anon, avec RLS actif).
  • Vérifier dans Supabase → Authentication → Policies qu'au moins une politique restrictive existe par table avant la mise en production de chaque église.
Ce n'est pas automatisable depuis ce dépôt Chaque église ayant son propre projet Supabase indépendant, ce rappel doit figurer dans votre guide utilisateur final (GUIDE_DEPLOIEMENT.html) ou votre onboarding client — pensez à l'y ajouter si ce n'est pas déjà fait.

3Rate limiting réseau (Vercel / Cloudflare) Recommandé si trafic important

Le code applique déjà un rate limiting applicatif basique (par IP + par compte) sur les routes sensibles (login, register, forgot-password, etc.) — voir lib/hub/rate-limit.js. Il tourne en mémoire par instance serverless : suffisant contre un script isolé, pas contre un attaquant distribué. Pour une protection robuste :

  1. Option simple : Vercel Firewall — Vercel → votre projet → Security → Firewall → activer une règle de limitation de débit sur /api/hub/* (disponible sur les plans Pro/Enterprise ; sur Hobby, privilégier l'option Upstash ci-dessous).
  2. Option robuste et gratuite à faible volume : Upstash Redis — créer une base sur upstash.com, ajouter UPSTASH_REDIS_REST_URL et UPSTASH_REDIS_REST_TOKEN dans Vercel, puis installer @upstash/ratelimit et brancher lib/hub/rate-limit.js dessus (le module est structuré pour ça).
  3. Option Cloudflare — si votre domaine passe par Cloudflare (proxy orange activé), Security → WAF → Rate Limiting Rules → limiter /api/hub/login et /api/hub/register à quelques requêtes/minute par IP.

4Révocation de sessions actives En cas de doute uniquement

Si vous soupçonnez qu'un compte spécifique (ou l'ensemble de la base) a été compromis :

  • Depuis le Super Admin Hub, invalider les sessions actives du compte concerné (force une reconnexion, invalide les session_token/refresh_token en circulation).
  • Informer l'église concernée de changer son mot de passe dès la reconnexion (bouton "mot de passe oublié" dans l'app, déjà fonctionnel).
  • Vérifier dans les logs du Hub (si disponibles côté Super Admin) les connexions récentes sur le compte concerné : IP inhabituelle, device_identifier inconnu.

5En cas de doute d'intrusion réelle Prioritaire

  1. Ne paniquez pas, mais n'attendez pas. Notez ce qui a été observé (message d'erreur, comportement anormal, alerte reçue) avec l'heure exacte.
  2. Rotation immédiate de toutes les clés listées en section 1, même sans certitude.
  3. Vérifiez les logs disponibles : Vercel → Deployments → Functions → logs des routes /api/hub/* (recherchez des pics de requêtes 401/403/429 inhabituels, signe de tentatives bloquées par les correctifs déjà en place).
  4. Contactez l'équipe Hub MbeukTechnologies si le doute porte sur le Hub lui-même (pas seulement sur ce SaaS) — eux seuls ont accès aux logs serveur du Hub central.
  5. Ne communiquez aucun secret (clé, mot de passe) pendant l'investigation, y compris à un outil d'IA — décrivez le symptôme, jamais la valeur du secret.

6Bonnes pratiques à maintenir dans la durée

✅ Déjà en place (à ne pas régresser)

  • Aucun secret dans le code client (vérifié par recherche exhaustive)
  • session_token/revoke-device/verify exigent une preuve de session
  • Validation stricte des emails/longueurs sur toutes les routes
  • Messages d'erreur génériques (pas de fuite d'existence de compte)
  • En-têtes de sécurité HTTP (vercel.json)

📌 À surveiller à chaque évolution du code

  • Ne jamais faire {...req.body} vers le SDK — toujours lister les champs explicitement
  • Ne jamais renvoyer error.details brut du SDK au client
  • Tout nouvel écran affichant une donnée externe → textContent, jamais innerHTML
  • Toute nouvelle route /api/hub/* → passer par requirePost + rejectIfBadOrigin + rate limiting dès sa création, pas après coup
